Section 3 — Working Logic Behind Each Component
3.1 — Document ingestion pipeline
This is the most complex component. The pipeline runs in Celery and has 8 stages. Each stage writes its output to the database before the next stage starts, so failures are recoverable.
Stage
What happens
Failure behaviour
1. Classify
Read MIME type + first 512 bytes. Detect: scanned PDF, digital PDF, image, audio. Store doc_type on Document.
Mark document FAILED. Stop.
2. Pre-process
PDF: check if digital (>100 chars text on pg 1). Digital: extract text per page via PyMuPDF. Scanned: pdf2image at 150 DPI. Audio: pydub chunks to 30s WAV files.
Mark FAILED if file corrupt.
3. Extract
Per page/chunk: call Gemma4OllamaService with appropriate method. Use schema prompt if schema_id provided, generic prompt otherwise. Parse + validate JSON response.
Retry page up to 3x. If all fail, store empty extracted_data with error flag.
4. Merge
Multi-page: call Gemma4 merge_results with all page extractions. Single page: pass through.
Use best single-page result on failure.
5. Validate
Check extracted JSON against schema field types. Compute confidence score (0-1) based on field completeness and type correctness.
Store with low confidence, flag for review.
6. Embed
Concatenate raw_text + extracted_data as string. Call Ollama embed endpoint with nomic-embed-text. Store vector on DocumentChunk.
Store chunk without embedding. Retry via separate task.
7. Classify dates
Gemma4 extracts all dates from document. Map to financial year. Store financial_year on Document.
Default to current FY.
8. Trigger recon
After all docs processed for a client, check if reconciliation should be re-run. If yes, enqueue ReconciliationTask.
Log warning, continue.
3.2 — Reconciliation engine
The reconciliation engine is the product's core differentiator. It runs a battery of deterministic checks across all documents for a client in a given financial year.
Architecture:
Each check is a ReconciliationCheck(id, name, description, severity, check_fn) dataclass
check_fn receives a ReconciliationContext — a structured object with all extracted data grouped by document type
check_fn returns a CheckResult(passed: bool, details: dict, flagged_values: list)
The engine runs all checks, aggregates results, caches the report in Redis by SHA256 of all input data
Cache TTL is 1 hour. Cache is invalidated when a new document is processed for that client+FY
The 10 built-in reconciliation checks:
26AS vs ITR: Compare TDS entries in Form 26AS against what client declared in their ITR draft. Flag mismatches above ₹1,000.
GST return vs invoice total: Sum all GST invoice amounts per GSTIN. Compare to GSTR-1 turnover declared. Flag deviation >1%.
TDS deducted vs TDS cert: Cross-check TDS amounts on salary slips against TDS certificates (Form 16/16A). Flag any gap.
Bank turnover vs P&L: Extract total credits from bank statements. Compare to gross revenue in P&L. Flag deviation >5%.
Expense 80C limit: Sum all 80C-eligible investments. Flag if total exceeds ₹1,50,000 statutory limit.
Cash transaction limit: Flag any single cash transaction above ₹2,00,000 (Section 269ST).
GSTIN format: Validate all GSTINs found in documents against the 15-character regex pattern.
PAN consistency: Verify PAN appears consistently across all documents (bank, ITR, GST). Flag any mismatch.
Date consistency: Check that all documents claim the same financial year. Flag outliers.
Missing deductions: If Form 16 shows medical allowance, check for Form 10BA / insurance premium receipts. Flag if supporting doc absent.
3.3 — LLM service abstraction
The Gemma4OllamaService wraps all Gemma4 calls. It must never be called directly from business logic — always injected as a dependency.
Key behaviours:
System prompt is fixed across all extraction calls: instructs model to return only valid JSON, never hallucinate, return null for missing fields
Temperature is always 0.1 for extraction (determinism). 0.3 for Q&A (some creativity).
Context window: 8192 for single-page extraction, 32768 for merge/Q&A to fit more context
All responses stripped of markdown fences before JSON parsing
If JSON parsing fails after stripping: retry call once with explicit instruction to fix JSON
Exponential backoff: 2s, 4s, 8s before giving up
Gemma4 E4B audio: base64-encode WAV, pass as 'audio' field in message alongside text prompt
Gemma4 E4B vision: base64-encode JPEG, pass as 'images' list in message
3.4 — Q&A service
The Q&A service answers natural language questions about a specific client's documents. It is always scoped to firm_id + client_id — never cross-client.
Query flow:
Embed the query using nomic-embed-text via Ollama
Run pgvector cosine similarity search on document_chunks filtered by firm_id AND client_id
Retrieve top-k chunks (default 8) above similarity threshold 0.65
Build a grounded prompt: chunks as numbered context blocks + user question
Call Gemma4 text endpoint with grounded prompt
Return answer + source chunk references so the CA can trace back to the original document
Audio queries: Gemma4 E4B audio input → transcribe + understand → same flow as text query
3.5 — Missing document tracker
Based on structured config (doc_requirements.yaml), the system knows what documents are required for each filing type and financial year combination.
Config structure (doc_requirements.yaml):
ITR-1:
  required:
    - Form 16 (from employer)
    - Bank interest certificates
    - 26AS / AIS
  if_has_house_property:
    - Home loan interest certificate
    - Municipal tax receipts
GSTR-3B:
  required:
    - All sales invoices for the month
    - All purchase invoices with GST
    - Bank statement (for reconciliation)
The tracker compares this config against what documents exist in the database for a client and returns a gap list with: document_type, required_for, severity (blocking / recommended), and a suggested message to send the client.
3.6 — Deadline tracker
All Indian statutory deadlines live in indian_tax_rules.yaml. The system does not hardcode dates — it computes them from rules (e.g. '15th of month following quarter end').
Key deadlines covered:
ITR filing: 31 July (non-audit), 31 October (audit required), 31 December (belated)
GSTR-1: 11th of following month (monthly filer), 13th after quarter end (quarterly)
GSTR-3B: 20th of following month
TDS return: 31st of month following quarter end (Q1: 31 July, Q2: 31 Oct, Q3: 31 Jan, Q4: 31 May)
TDS payment: 7th of following month (March: 30 April)
Advance tax: 15 June (15%), 15 Sept (45%), 15 Dec (75%), 15 March (100%)
Per client, the tracker: reads client.filing_type and client.gstin to determine which deadlines apply, extracts relevant dates from processed documents to confirm coverage, returns a deadline calendar sorted by due_date with days_remaining computed at query time.

Section 5 — Critical Implementation Notes
Multi-tenancy enforcement
CRITICAL:  Every single database query MUST include a WHERE firm_id = :firm_id clause. Build a helper get_or_404(db, Model, id, firm_id) that raises 404 if the record doesn't belong to the requesting firm. Use this everywhere. Never use db.get(Model, id) directly.
Pattern to enforce in every service method:
async def get_document(db: AsyncSession, doc_id: UUID, firm_id: UUID) -> Document:
    result = await db.execute(
        select(Document).where(Document.id == doc_id, Document.firm_id == firm_id)
    )
    doc = result.scalar_one_or_none()
    if not doc:
        raise HTTPException(404, 'Document not found')
    return doc
Local vs Docker compatibility
NOTE:  The application code must not know whether it is running in Docker or locally. All service URLs (Postgres, Redis, Ollama) come from environment variables. .env.local has localhost URLs. .env.docker has container service names. The Makefile sets the correct env file automatically.
# .env.local
DATABASE_URL=postgresql+asyncpg://docint:docint@localhost:5432/caintel
REDIS_URL=redis://localhost:6379/0
OLLAMA_BASE_URL=http://localhost:11434
# .env.docker
DATABASE_URL=postgresql+asyncpg://docint:docint@postgres:5432/caintel
REDIS_URL=redis://redis:6379/0
OLLAMA_BASE_URL=http://ollama:11434
Celery task reliability
CRITICAL:  Set task_acks_late=True and worker_prefetch_multiplier=1. This ensures a task is only acknowledged AFTER it completes — if the worker crashes mid-task, the task re-queues. For GPU-bound Gemma4 calls, concurrency=1 per worker is mandatory to prevent VRAM OOM.
Gemma4 prompt engineering
The extraction prompts are the hardest part to get right. Ship these system and user prompt templates — do not let the agent make them up:
System prompt (use verbatim):
You are a document intelligence engine for Indian CA firms.
Rules:
1. Extract ONLY what is explicitly present. Never infer or hallucinate.
2. Return null for any field not found in the document.
3. All monetary values: numbers only, no currency symbols (e.g. 150000 not ₹1,50,000).
4. All dates: ISO 8601 format YYYY-MM-DD.
5. All PAN: uppercase, no spaces.
6. All GSTIN: uppercase, 15 characters exactly.
7. Respond ONLY with valid JSON. No explanation, no markdown fences.
Indian document-specific context to include in user prompts:
For bank statements: look for closing balance, total credits, total debits, OD limit if mentioned
For Form 26AS / AIS: extract each TDS entry as {deductor_name, tan, amount_deducted, amount_deposited, pan}
For salary slips: extract gross salary, basic, HRA, special allowance, TDS deducted, PF deducted, net pay
For GST invoices: extract all line items, CGST and SGST separately, validate CGST rate == SGST rate
For Form 16: extract Part A (TDS deducted) and Part B (income breakdown) separately
pgvector index configuration
Create the IVFFlat index with lists=100 for up to 1M rows per firm. If a firm has fewer than 1000 document chunks at query time, pgvector will fall back to sequential scan — this is acceptable and expected.
CREATE INDEX ON document_chunks USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

7.4 — API integration patterns
All API calls should follow these patterns:
// Base API client setup
const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL + '/api/v1',
  timeout: 300000  // 5 min for Gemma4 processing
})
// Interceptor to add JWT
api.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
// Poll job until complete
const { data: job } = useQuery({
  queryKey: ['job', jobId],
  queryFn: () => api.get(`/jobs/${jobId}`).then(r => r.data.data),
  refetchInterval: (data) =>
    data?.status === 'completed' || data?.status === 'failed' ? false : 3000
})
